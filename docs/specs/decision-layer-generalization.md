# 决策层泛化：让用户能扩展判断能力

## Problem Statement

现在的判断能力只能服务记忆。用户想让它也管别的——浏览器操作前要不要执行、某条命令要不要确认、一次任务要不要拆解——但每加一种判断，都要改插件的代码并发版。

具体地说，用户遇到三个障碍：

第一，**判断的种类被写死。** 决策记录里带着 `recall_gate`、`scope_global` 这样的字段名，界面上分类是「记忆查询 / 记忆录入」。当一条判断是关于命令安全的，没有位置安放它，界面上也无从显示。

第二，**判据不在用户手里。** 实测表明判断准不准主要取决于判据怎么写——同一句 `rm -rf`，判据写模糊时被判为 safe 74%，把判据写清楚后结果改变。但判据现在写在代码里，用户遇到误判只能等发版。

第三，**没有统一的地方看判断记录。** 用户想知道「它到底判断了些什么、选了什么、为什么」，现在只能看记忆那部分的轨迹。

## Solution

把「决策点」做成可配置的扩展单元。一个决策点声明四件事：在哪儿触发、能看到什么、问什么、选完之后做什么。用户能新增自己的判断，不需要等插件发版。

用户可以在设置里：

- 看到所有已启用的决策点，按判断类型分类
- 调整每个决策点的判据文本
- 开关单个决策点
- 把自动化等级调得更保守（但不能调得比作者设计的更激进）
- 在决策记录里按类型查看每一次判断：问了什么、有哪些选项、选了什么、置信度多少、最后执行成了什么

判断记录按「判断主体」分类展示，记忆只是其中一类。

## User Stories

1. 作为用户，我想让插件在我发消息时判断这条消息要不要查记忆，这样我不必每次都说「查一下记忆」。
2. 作为用户，我想让它同时判断这条消息是否包含值得记住的内容，这样我提供的稳定事实和纠正会被保存。
3. 作为用户，我想让这两件事分开判断，因为一条消息可能不需要查但要记住，或者需要查但无需记。
4. 作为用户，我想在一条命令执行前判断它是否危险，这样破坏性操作会先问我。
5. 作为用户，我想给浏览器操作加上判断，这样某些动作不会在我不在的时候悄悄发生。
6. 作为用户，我想自己新增一个判断点，比如「前端改样式时要不要跑 lint」，而不必等插件发版。
7. 作为用户，我想调整某个判断点的判据措辞，因为我知道在我的场景里什么叫「危险」。
8. 作为用户，我想关掉某个判断点，如果它对我的项目没有意义。
9. 作为用户，我想把某个自动执行的判断改成先问我，如果我发现它判得不够准。
10. 作为用户，我想在界面上按类型筛选判断记录，比如只看「记忆查询」或只看「命令安全」。
11. 作为用户，我想看到每次判断问了哪些问题，这样我能判断判据写得对不对。
12. 作为用户，我想看到每个问题提供了哪些选项，以及模型选了哪个。
13. 作为用户，我想看到每次选择的置信度，这样我知道哪些判断是勉强的。
14. 作为用户，我想看到判断最终落实成了什么动作，以及执行结果如何。
15. 作为用户，我想看到判断的耗时，这样我知道它是否拖慢了响应。
16. 作为用户，我想在手机上也能正常查看这些记录，因为我经常在手机上用。
17. 作为用户，我想在设置页测试决策模型连接时，知道它是否支持批量判断，因为那影响一组判断要花多久。
18. 作为用户，我想让同一轮里互不依赖的判断合并成一次请求，因为那样更快。
19. 作为用户，我想让有依赖关系的判断按顺序执行，因为后一个的选项取决于前一个的结果。
20. 作为用户，我想在判断模型挂掉或超时的时候，插件照常工作，只是暂时不做那些判断。
21. 作为用户，我想在判断接口不支持批量时，它自动退回逐次调用，而不是报错。
22. 作为用户，我想让判断记录的体积有上限，这样长会话不会把记录撑爆。
23. 作为用户，我想让敏感内容不进判断状态，比如环境变量的值。
24. 作为插件作者，我想新增一个判断点时只写声明、不碰决策层的代码。
25. 作为插件作者，我想让用户写的判断点和我内置的走同一套校验，这样用户配错了在加载时就报错。
26. 作为插件作者，我想让自动化等级由我定默认值，用户只能收紧，这样我设计时没考虑到的误判不会悄悄生效。
27. 作为开发者，我想在判断记录里看到它来自哪个判断主体，这样排查时知道是哪一环出的问题。
28. 作为开发者，我想让旧格式的判断记录仍然能显示，不因为结构变了就丢失历史。

## Implementation Decisions

### 决策点作为声明式单元

一个决策点由四部分组成：触发位置、可见状态、问卷、落点动作。落点动作是封闭集合（`proceed` / `skip` / `ask` / `inject` / `store` / `route`），用户只能组合不能发明，因此执行器在运行时不会遇到未知动词。

判据对用户可编辑，这是准确率的主要来源。

### 判断状态是白名单

判断模型不做推理，长状态不会帮它想得更多，只会稀释判据。因此判断状态是显式允许列表，包含当前消息、候选集合、环境摘要这类有限字段，不包含完整对话历史。超长字段截断，并记录截断事实——读了半条消息得出的答案仍是答案，但看记录的人应当知道它没看全。

### 自动化等级单向收紧

作者定的等级是自主性的上限。用户可以把「静默执行」改成「先问我」，但不能反过来。超出作者允许的请求静默 clamp 而非报错，因为为了一处用户看不见的差异让插件不可用并不值得。

### 依赖排序

判断之间有两种关系：独立的可合并进一次请求，有依赖的必须串行且后者的选项由前者决定。依赖由决策点自己声明，编排层按拓扑序执行。依赖成环是声明错误，在加载时抛错而不是运行时猜测。

### 记录结构去记忆化

记录结构加入判断主体字段，其余部分（问了什么、选项、答案、置信度、落实动作、结果）对所有判断主体一致。界面按判断主体分类，记忆相关的展示细节属于视图层，不属于数据层。

旧记录没有判断主体字段，按记忆判断解释，不清空历史。

### 能力探测与降级

配置只需要一个基础地址。批量能力在首次使用时探测并缓存；探测失败不是错误，退回逐次调用是正常路径。测试连接时把批量能力显示给用户。

### 落点动作的执行接线

命令安全接到 `tools/pre-execute`，可以真正放行、拒绝、取消或询问用户。判断输出的是严重程度（可逆 / 破坏性 / 未知 / 超出范围），是否询问由自动化档位决定：作者定默认，用户只能收紧。授权过的同类调用由 `ctx.tools.guard()` 单调守卫兜底，后续监听器不能把拒绝改回允许。没有审批服务时按拒绝处理（fail closed）。

> **修正（2026-10-29）**：本文早先断言「DSH 没有工具调用前的钩子」，这是错的，而且这条错误断言正是记忆路径一直绕开真正拦截点的原因。`tools/pre-execute` 是官方扩展点，`@deepseek-ai/dsh-tools` 的类型定义里写着它可以 `allow / deny / cancel / ask`，拒绝后还有单调守卫层。
>
> 当初选 `agent/pre-step` 是**产品选择**：按本轮意图判断比逐条命令拦截更省 token、更少打断。这是取舍，不是平台限制。两者可以并存——`agent/pre-step` 仍然承载记忆读写，`tools/pre-execute` 承载逐调用安全。

## Testing Decisions

好的测试只验证外部行为，不验证实现细节。具体到这件事：

**测什么**

- 决策层的编排：独立的判断合并进同一批，有依赖的排到后一批，成环报错。这是外部可观察的行为，不涉及内部数据结构。
- 校验：判据为空、选项少于两个、动作不在封闭集合内，都应在加载时被拒绝。这测的是「配错了会怎样」，而不是「校验函数怎么写」。
- 自动化等级的收紧与 clamp：测的是用户设置生效的结果，不是比较逻辑本身。
- 判断状态白名单：测的是「模型看到了什么」，可以直接对着发出去的请求断言。
- 记录结构：断言它不包含记忆专用词汇，这样第二个判断主体接进来时不需要改记录层。
- 判断点加载：内置的和用户写的走同一套校验，一个合法的用户声明和一个非法的用户声明各自的结果不同。
- 批量探测与降级：对支持批量的端点发一次探测后不再重复探测；对不支持的端点，每个请求仍然得到回答，只是改走单独调用。
- 遍历记录渲染：用真实记录结构走一遍视图，断言关键字段出现在输出里。

**在哪里测**

优先用已有的最高接缝。编排层本身就是最高接缝——它接受一个注入的判断适配器，测试里用假的适配器替换真实模型，不需要 mock HTTP。现有的集成测试已经这么做。

对于判断点声明和校验，接缝是加载函数：喂进去一组声明，断言接受或拒绝。

对于界面，接缝是视图组件本身：喂进去一份记录，断言渲染结果。已有类似做法。

**先例**

现有的适配器测试用假的 `fetchImpl` 验证请求形状与降级路径；现有的 host 测试用假的编排器验证准入；现有的轨迹测试用重放验证记录重建。这些模式直接复用，不引入新的测试基础设施。

## Out of Scope

- **不做通用 Agent 框架。** 判断仍是单点、封闭选项、无推理链。需要长上下文的复杂问题归主模型。
- **不让用户在运行时写代码。** 决策点是声明，不是插件。要执行自定义逻辑仍然得写代码。
- **不做自定义触发位置。** 触发位置先由插件内置并命名，用户只能在自己的判断点里选，暂不支持挂到任意钩子。
- **不做判断质量的自动评估。** 记录让人回看，但不自动判断「这次判得对不对」。
- **不改记忆本身的逻辑。** 本规格只做泛化与接线，记忆的检索、留存、注入行为不变。

## Further Notes

一件实测出来的事实值得记下来：判断准不准主要取决于判据措辞，而不是模型。同一句 `rm -rf` 在判据写「判断危险程度」时被判为 safe 74%，把判据改成具体描述不可逆后果后结果改变。这说明让用户能改判据不是可有可无的便利，而是这门能力可用的前提。

另一件：批量确实省时间但不是魔法。同一网关下，单次调用约 100–350ms，10 条批量约 400ms，32 条约 1.25s，64 条约 2.46s——基本线性。所以批量的价值在于省掉多次往返，而不是让大量判断变便宜。依赖排序的意义也在这里：不该为了凑批量去问一个不适用的判断。

反过来说，同一主体上的多个问题合并在一次调用里几乎不增加成本（4 个问题约 330–850ms），这是应当充分利用的。
