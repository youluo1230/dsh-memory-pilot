# 决策能力的组织方式

MemoryPilot 用窄判断模型（SystemOne 协议）替代"让大模型凭感觉决定"的地方。这份文档记录一次调用里怎么把判断组织起来，以及为什么这样分。

## 一个请求里可以承载多个判断

一次 `/systemone` 调用可以同时回答多个带判据的问题，返回每个问题各自的选择与校准概率。这比拆成多次调用更省时间，也避免了各次调用之间的状态不一致。

实测（同一网关，`clef-flash`）：

| 组织方式 | 实测延迟 |
|---|---|
| 单次调用、单问题 | 约 280–350 ms |
| 单次调用、4 个问题 | 约 330–850 ms |
| 批量端点 10 条请求 | 约 400 ms |
| 批量端点 32 条请求 | 约 1.25 s |
| 批量端点 64 条请求 | 约 2.46 s |

结论：**同一主体上的多个问题应当合并为一次调用**，成本几乎不随问题数量增长。跨不同主体的判断用批量端点，但批量并不节省比例时间，只是省去多次往返。

## 哪些判断必须分先后

判断之间存在依赖时，后一个判断的选项取决于前一个的结果。这类必须串行，且后一个问题只在需要时提出。

记忆处理就是这种结构：

```
是否要读记忆 ──none──> 不读
      │
    memory
      ↓
  用哪种读法 ──> 查哪些范围 ──> 读
是否要写记忆 ──discard──> 不写
      │
    retain
      ↓
  写到哪个范围 ──> 写
```

读与写是**两条独立分支**，并行成立于同一份问卷。但每个分支内部有依赖：不读就无需问读法，不问范围就无从选库。

因此实现上：读和写的门控放在同一次调用里问，但"用哪种读法""查哪个范围"这类跟随问题只在门控通过后才生效——即使它们被一并提问，其结果也只在门控允许时才被采用。

## 哪些可以合并

同一主体、互不依赖的判断：

- 一段消息是否需要读记忆 / 是否需要写入记忆
- 多个候选动作分别是否可接受
- 同一条内容在多个候选库里各自是否需要留存

这些合并在一次调用中提问，任何一个的答案都不影响其余的选项。

## 请求形状的探测

服务端支持批量，但不同部署（自建、中转、直连）不一定都开放 `/v1/systemone/batch`。配置只要求一个基础地址，能力在首次使用时探测并缓存：

1. 用最小批量请求试探批量端点
2. 可用则记录，后续小判断走批量
3. 不可用则退回逐次调用，行为完全一致

探测失败不能视为错误——降级是正常路径，不是异常。
