# 重新定位：从记忆插件到决策层

## 现状与问题

当前实现把一个通用能力（窄判断模型）绑在了一个具体场景（记忆）上。代码里 `core.mjs` 的编排、`trail.mjs` 的记录、`host.mjs` 的准入，全都假定判断对象是记忆读写。结果是：

- 决策记录的结构里写死了 `recall_gate`、`scope_global` 这些记忆专用字段
- 想加一个"这条命令要不要问用户"的判断，要改四处
- 轨迹里只能显示记忆相关的表格

但这个能力的本质不是记忆。**窄判断模型能做的是：给定状态，在封闭选项里选一个，并给出校准概率。** 记忆只是它第一个、也是最复杂的使用者。

## 目标形态

一个决策层，多个判断主体（subject）。记忆是其中一个 subject，不是全部。

```
decision layer
├── subject: memory.read      是否读记忆 / 读哪个库 / 用什么读法
├── subject: memory.write     是否写入 / 写到哪个库
├── subject: command.safety   这条命令是否危险
├── subject: task.routing     这个请求要不要拆解
└── subject: <future>
```

每个 subject 声明三件事：

1. **状态**：判断需要看到什么（消息、上下文、候选集）
2. **问卷**：问哪些问题、每个问题的选项与判据
3. **落实**：选完之后产生什么动作

决策层负责：能力探测、批量编排、依赖排序、超时降级、结果记录。它不知道"记忆"是什么。

## 依赖与排序

判断之间有两种关系，必须区分：

- **独立**：同一状态上的多个问题，可并进一次调用。例如"要不要读"和"要不要写"。
- **依赖**：后一个判断的选项由前一个的结果决定。例如不读就无需问读法。

依赖关系由判断点自己声明（`depends: ['memory.read']`），编排层按拓扑序执行。同一层内的判断合并成一次请求——这是批量真正的用武之地，不是把无关的判断硬凑一起。

> **2026-10-29 修正**：本节早先写的是 `after`，而声明里写的是 `depends`。`planStages` 读 `after`、声明写 `depends`，两者从未对上，所以依赖排序一直是惰性的：所有判断点都落在第 0 层，声明的顺序只是装饰。现在统一到 `depends`，并且真的按排序执行；成环在加载时抛错。字段名统一这件事本身值得记一笔，因为它说明「声明写了但没人读」这类失效不会被任何行为测试发现——只有断言顺序的测试能抓。

判断点内部的依赖（例如会话蒸馏的「先粗筛整轮，再逐条判断候选」）用 `questionDepends` 声明，由 `src/decision-executor.mjs` 的 `questionStages` 处理。它和 `depends` 是不同层的东西：前者排的是问题，后者排的是判断点。

## 加载时的两道检查

两件事必须在加载时就报错，否则失效会一直静默：

- **声明的字段运行时拿不到**（`unprovidedStateFields`）。`memory.read` 声明了 `residentDigest`，而 `host.mjs` 从不提供它——判断点看起来在，实际在拿一个永远为空的值判断。现在这类声明在加载时就抛错，运行链路也必须真的提供它声明的每个字段。
- **某个触发位置没有落点**（`landingFor`）。一个声明存在但运行时从不加载的判断点，是最难发现的失效。触发位置没有任何落点接收，就是错误，不是「悄悄不判」。

## 记录与查看

记录结构改成 subject 无关：

| 字段 | 含义 |
|---|---|
| subject | 哪个判断主体 |
| questions | 问了什么、有哪些选项 |
| answers | 选了什么、置信度 |
| outcome | 落实成了什么动作、结果如何 |

界面按 subject 分类展示，而不是写死"记忆查询/记忆录入"。记忆 subject 可以有自己的展示细节，但那属于视图层，不属于数据层。

## 迁移路径

不能一次性重写。按这个顺序：

1. **抽出决策核心**：把"问卷→调用→动作"的通用部分从记忆逻辑中分离，记忆成为第一个 subject 实现
2. **记录结构 subject 化**：加 `subject` 字段，旧记录按 `memory` 解释
3. **接入第二个 subject**：用它验证抽象是否真的通用。选一个最小的（如命令安全检查），不要一上来就做大
4. **界面泛化**：分类改为按 subject，记忆的细节作为 subject 专属视图

第 3 步是关键验证点：如果第二个 subject 接入时还要改动决策核心，说明抽象错了。

## 与现有插件的关系

`dsh-jev-decide` 把判断做成 agent 可调的工具——由模型自己决定何时调用。这是自上而下的用法，适合"模型知道自己需要判断"的场景。

本层是自下而上的：编排层在固定位置自动判断，模型不参与。两者不冲突，可以并存——工具是给模型的一把锤子，本层是给插件作者的一套装配线。

## 不做什么

- 不做通用 Agent 框架。判断仍然是单点、封闭选项、无推理链。
- 不让决策模型处理需要长上下文的复杂问题。那是主模型的事。
- 不为每个 subject 造一套独立基础设施。共用探测、编排、记录。
