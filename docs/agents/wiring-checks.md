# 接线检查：为什么这类测试必须存在

`test/wiring-contract.test.mjs` 不是普通的回归测试。它守的是一类**行为测试抓不到的失效**，所以不要因为它"看起来在测实现细节"而删掉它。

## 这一类失效长什么样

在 #3 的实施里出现过三次，形态完全相同：

| 失效 | 表现 | 为什么行为测试没抓到 |
|---|---|---|
| 记忆判断点的声明从未被加载 | 声明存在、校验通过、设置面板能显示，运行时用的是适配器里的私有字面量 | 每个测试自己注入了假的 decision，夹具把生产漏掉的东西补上了 |
| `runtime.decision` 从未挂到 runtime 对象 | 工具安全和会话蒸馏三处读它，全是 `undefined`，两整条链路在生产里没跑过 | 同上：注入假协作对象的测试看不见"没人给它" |
| 用户声明被**追加**而非替换内置点 | 改判据后列表里有两个同名点，`find` 命中内置，用户的修改永远不生效 | 请求形状与内置完全一致，只有"改一条再比对"才能区分 |

共同结构：**生产者与消费者之间没有断言**。代码读一个东西，而没人产它；或者产了但下游拿到的是别的副本。

## 为什么行为测试必须抓不到

这不是测试写得不够多。`#3` 有 359 项测试，其中大量是行为测试。它们抓不到的原因是结构性的：

> 行为测试要驱动一条链路，就必须注入链路上的每个协作者。而"生产环境忘了接某个协作者"恰恰是**夹具替你接上了**的那一个。

所以凡是"某东西没接上"的缺陷，靠增加行为测试覆盖永远抓不到。必须有一个测试**不做注入**，直接看装配后的产物。

## 现有的四个检查

1. **源码扫描：runtime 消费者必须有生产者**。扫 `runtime.X` 的读取，与 `const runtime = {...}` 的键比对。新增一个消费者时自动覆盖，不依赖有人想起来补测试。
2. **装配后走真实 hook 的拒绝链路**。`apply()` 之后驱动 `tools/pre-execute`，断言破坏性判断真的导致 `deny`、工具体没跑。这是唯一能证明"判断传输真的被调用"的测试。
3. **改一条声明，看它是否到达请求**。这条是关键：只断言"请求里有 `recall_gate`"是无效的，因为回退到内置声明时形状完全一样。必须改一条判据再比对内容。
4. **挂上的 hook 必须可调用**。注册了但一调就抛，是同一类失效的下一个层次。

## 新增能力时该做什么

问一句：**这个东西在生产的装配点上，有没有人真的把它交出去？**

如果有，就在 `wiring-contract.test.mjs` 里加一条断言。具体做法：

- 加消费者 → 检查 1 自动覆盖它，只要字段真的在 runtime 字面量里。
- 加一个 RPC 端点或 hook → 断言它在 `apply()` 之后可调用，并且端到端走一次真实路径。
- 加一个可编辑的配置项 → 断言**改它之后行为变了**，而不是断言"它被保存了"。第二件事已经有人管，第一件事没人管。

## 相关的既有约定

- `docs/agents/decision-layer.md`「加载时的两道检查」：声明了拿不到的字段、没有落点的触发位置，加载即报错。那是同一思路在运行时的版本。
- `docs/adr/0002`「必须守住的一条」：一个声明存在但运行时从不加载的判断点，是最难发现的失效。这一个文件就是那句话的执行方式。
