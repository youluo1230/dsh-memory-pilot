# 会话蒸馏与工具安全拦截

这两个能力共用同一条判断链路（声明 → 问卷 → 答案 → 落点），差别只在于触发位置和落点。放在一篇里写，是因为它们一起证明了决策层不是「记忆专用」的：新增一个判断点只写一份声明加一个落点，不改判断层。

## 会话蒸馏

### 它要解决的问题

原来的「自动记录」是**无筛选的原始留档**：每轮结束把用户原文与助手原文整段拼起来投给后端，不经过任何判断。它记录的是对话流，不是对话得出的结论。用户想要的「从这次讨论里把结论挑出来记住」这件事完全没有发生。

蒸馏和 turn capture 是两件事，不要混：capture 存对话流，不选择任何东西；蒸馏在结束信号处**选择**这次对话产出的、未来会话会因此出错的那些内容。两者并存，各自独立失败。

### 结构

两级判断，写在同一份声明里（`session.distill`）：

1. `turn_worth_keeping`：一个问题，判整轮值不值得留存。**预期大部分轮次在这里被丢掉**——这是成本控制，不是失败。拒绝之后第二级根本不会发问。
2. `candidate_selection`：值的话，把候选逐条判 retain / discard，**全部放进同一次请求**。实测同一主体上的多个问题合并请求几乎不增加成本（四个问题约 330–850 毫秒），逐条调用会把这笔延迟付好几遍。

**候选由插件切分，判断模型只能在给定候选里选，不能凭空生成。** 落进常驻记忆的文本是被选中的原句，不是模型写的摘要——窄判断模型不生成文本，让它写摘要就是拿短处去干主模型的事。候选数量有上限（`MAX_CANDIDATES`），因为长状态会稀释判据，判断模型的可见状态字符上限本身就是为这件事设的。

### 触发

两处，都不是定时器：

- **归档会话**（`workspace/session-activity`）。归档是用户表达「这段结束了」的最强信号，而且它是可 await 的——平台在写归档集之前调用这个 waterfall，所以蒸馏能在会话上下文还活着的时候跑完。注意 `stopActivity: true` 的归档路径不做活动检查、直接写归档集，所以这条钩子不是每次归档都会触发；这不影响正确性，因为 8 轮兜底还在。
- **轮次阈值兜底**（默认八轮，可配置，0 表示只靠归档）。给一直不归档的会话用：关掉浏览器不该漏记。

**不做空闲定时器**：平台没有空闲事件，自己维护定时器的收益抵不上复杂度。这是一个刻意的省略，不是遗漏。

### 键与去重

键由内容的主体部分派生（`factKey`），**不是内容哈希**。用哈希作键虽然能去重，但修正事实时会产生第二条，而「修正一条已存事实」是这类记忆最常见的更新方式。所以 `端口是 8080` → `端口是 9090` 必须落到同一个键上：那是同一个事实的值变了，不是两个事实。

判断的状态里带上常驻段落已有的键列表，要求它复用已有键或明确新建。显式记忆工具与自动蒸馏**写同一套存储、共用同一个保留路由**，因此键机制天然去重：显式记过的东西蒸馏时会用同一个键覆盖，不需要额外的协调逻辑。

### 常驻写满

降级到外部后端，不是写入失败。文件满不是用户的修正应该消失的理由。**不做**常驻记忆的淘汰或合并（本期不做，写满只降级）。

### 部分失败

一个候选写失败不丢掉已经写成功的那些。报告如实写：`retained` 列出落地的，`failed` 列出没落地的和原因码。

## 工具安全

### 它要解决的问题

原来在 `agent/pre-step` 上跑，只能往上下文里塞一句提示，**拦不住任何东西**。仓库文档那句「DSH 没有工具调用前钩子」是错的，而这条错误断言正是记忆路径一直绕开真正拦截点的原因。

### 挂在哪里

`tools/pre-execute`——官方扩展点，可以 `allow / deny / cancel / ask`。`ctx.tools.guard()` 在其后提供**单调守卫**：它只能拒绝，不能放行，所以后续监听器无法把拒绝改回允许。这才是「我的拒绝真的生效」的实现。

> 坚持在轮次级判断（`agent/pre-step`）承载记忆读写，是**产品选择**（省 token、少打断），不是平台限制。两者并存。

### 判断输出什么

**严重程度**，四档：可逆 / 破坏性 / 未知 / 超出范围。判断**不**决定要不要问——那由自动化档位决定。作者定默认，用户只能收紧（`resolveAutomationTier` 把放宽夹回作者的档位）。

四种严重度的落点：可逆与未知放行（不知道不等于危险，对「不知道」发问会训练用户盲点通过），破坏性与超出范围发问。`silent-visible` 档下危险操作仍然放行但留记录。

### 询问道径

用平台的审批请求（`approval/request`）。只能在打开的轮次内发起；**没有审批服务时按拒绝处理（fail closed）**——「没人能说可以」不等于「当作可以」。

### 单调守卫的指纹

同类判定的指纹在插件内按会话维护（`callFamily`：工具名 + 参数形状，把易变的部分归一）。一次授权覆盖这一家族，多步任务不会被打断十次。只有**授权**是单调的：拒绝不记入指纹，否则用户说过一次不该问的，就再也不会被问。

## 失败可见

检索与写入失败至少留一条简短、不含凭据的日志，并在设置里提供「最近记忆活动」列表：每行含类型（查 / 记 / 蒸馏）、时间、成败、耗时、失败时的短错误码。行里**只走短码，不走依赖的错误消息**——存储的错误文本可能引用文件内容，或者更糟，引用一个鉴权头。

## 本期不做

- 判断质量的自动评估或用户反馈回路（记录让人回看，但不自动判「这次判得对不对」）。
- 常驻记忆的淘汰或合并（写满只降级）。
- 空闲超时触发蒸馏（平台没有空闲事件）。
- 摘要式蒸馏（只挑选原句）。
- 改造 MemOS HTTP 后端（仍是只读检索）。
