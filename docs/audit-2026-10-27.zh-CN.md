## 决策轨迹：为什么换了实现方式

你要求在轨迹里看到「面对什么样的问题，发了什么请求，做了什么选择」。第一版用 `plugin/observation` 会话事件承载，这版**必须推翻**，原因写在 DSH 自己的插件规范里：

- 持久层只认内置事件类型，未知类型必须带 `ignorable: true` 才能被跳过，而在线 `Session.append()` **无法**设置这个标记 → 会话历史直接加载失败（就是最初那个 bug）。
- `appendPluginRecord()` 能写 ignorable 记录，但文档明确它**保留给 DSH 实验性包**，第三方插件不该依赖（格式迁移只做尽力保留）。

所以现在走官方给第三方插件的正规通路，分两半：

| 环节 | 做法 | 位置 |
|---|---|---|
| Host 产出数据 | `ctx.sessionProjections.register()` 注册一个 projection，`wire.view` 把算好的值推给浏览器 | `src/trail.mjs` |
| 决策落地 | 决策发生在 `agent/pre-step`，那一刻还没有属于该步的事件，因此先挂在有界的待发布表里，由该步第一个已提交事件（`step/start`）折叠进投影 | `src/trail.mjs` `createDecisionTrail` |
| 轨迹渲染 | `ctx.uiConversation.events.register()` 注册 trajectory 定义，按 turn/step 定位，节点是 `context` cell | `lib/client.js` |

这样**日志里不新增任何事件类型**，「会话历史打不开」这个 bug 从机制上不可能复发（已加断言测试守住）。

轨迹行会显示：你的问题原文、决策模型与判定耗时、模型被问的每个问题及其所选档位（含概率）、被策略授权的动作、每个动作实际打到的后端/操作/命中数/耗时、以及注入主模型多少字符。

## 先说结论

插件**核心链路是好的**：决策模型协议正确、证据校验严格、作用域绑定拒绝模型越权、写入有 revision 栅栏。
真正的问题集中在**三处**：

1. **作用域/库（bank）这套抽象和实际部署对不上** —— 项目级记忆现在**一条都查不到**（见 P1）。
2. **配置项与运行时脱节** —— 滑杆能改但不生效、开关能关但副作用没告知（见 P2、P4）。
3. **失败静默** —— 检索失败、捕获失败都不告诉任何人（见 P3、P5）。

## P1（严重，已修复）项目级记忆全部查不到，且 UI 建不出来库

**现象**：用你的真实配置跑完整链路，项目级检索稳定返回 `status=error`，主模型拿到的上下文是空的。

```
生效 bindings: memos-global@global, hs-repository@project
orchestrator 结果 716 ms status=error
executions: [{"scope":"project","op":"search","status":"error"}]
```

**修复（0.3.17）**：`create-bank` RPC 后端一直实现着，但前端 `form.createBank` 定义了从没被调用，导致「库不存在」只能靠手工在 DSH 外面建。现在「使用范围」表里，状态为「尚未创建」的行会直接显示**创建库**按钮，创建成功后自动刷新检测结果。根因（bank 不存在）没有改变，改变的是**用户能不能在界面里把它补上**——这才是真正的堵点。

**根因（实测）**：`coding-agent::{project}` 会展开成 `coding-agent::dsh-memory-pilot`，但 Hindsight 里**不存在这个 bank**：

```
❌ 不存在  coding-agent::dsh-memory-pilot   ← 插件会去查
✅ 存在    coding-agent::code                ← 实际有 279 条
✅ 存在    coding-agent::geo
❌ 不存在  coding-agent::sparkDash-fnos
```

Hindsight 实际只有：`hermes`(4472)、`omp`(32702)、`hermes_pc`(1469)、`coding-agent::dgx`(943)、`coding-agent::code`(279)、`coding-agent::workspace`(58)、`coding-agent::app`(54)、`coding-agent::.dsh`(40) 等。

也就是说：**你在 `code` 目录下的 279 条历史记忆，插件一条都没读到**，因为它按仓库名去找了一个不存在的库。

**更糟的是 UI 无法补救**：`create-bank` 这个 RPC 服务端完整实现、客户端也封装了 `form.createBank`，但**前端从来没调用过它**。

```
UI 实际调用的 form 方法: getSnapshot, subscribe, test, discover, residentGet, mutate, residentPut
定义但从未调用: createBank
```

「使用范围」页里状态显示「尚未创建」的五行，全是只读文本，没有一个「创建」按钮。

**建议**：① 把「尚未创建」变成可点的「创建库」按钮，接 `form.createBank`；② `targetsFor` 在 bank 不存在时回退到工作区级 bank（`coding-agent::{workspace}`）或明确标红。

## P2（已修复）预算滑杆形同虚设

原代码：`retrievalBudgetMs: () => Math.max(current().budgetMs ?? 9000, 60000)`，而 schema 上限是 30000。
**任何用户能选的数值都会被 60000 覆盖**，而且外层 60s 与内层 9s 互相打架（内层 timeout 后外层还在等）。

已改为「内层 deadline + 余量」，让内层先超时并产生可读的 `timeout` 状态：

| 设置 | 修复前外层 | 修复后外层 |
|---|---|---|
| 2500 ms | 60000 | 17500 |
| 9000 ms | 60000 | 24000 |
| 30000 ms | 60000 | 45000 |

新增回归测试 `test/budget-floor.test.mjs`（4 项）。

## P3（严重，未修）检索/捕获失败完全静默

- `directRetrieve` 把失败的 backend 折成 `failed=true`，最后只返回 `status:'error'`，**不记日志、不报错**。
- `captureTurn` 走 `Promise.allSettled`，失败被吞掉，**没有任何审计记录**。实测一次捕获耗时 **12.5 秒**，期间用户毫无感知。
- 只有一个 `capture: () => ... global scope + write` 的布尔开关决定要不要自动捕获；用 Hindsight 做项目记忆的用户，**自动捕获永远不触发**（Hindsight 没实现 `captureTurn`）。

**建议**：失败写一条 `log('warn', ...)`；UI 加一个「最近记忆活动」列表（成功/失败/耗时），否则用户永远不知道记忆是不是在工作。

## P4（已部分修复）自主模式会静默关掉常驻记忆

`decisionEnabled=false` 时 `decision=null`，于是 `retentionRouter=undefined`，**USER/全局 MEMORY/项目 MEMORY 的自动维护整条停摆**。
UI 文案只写了「由模型自行调用工具」，**没提常驻记忆失效**。

代码注释里承认了这一点（"that path stays closed here"），但没有暴露给用户。

**建议**：UI 在关闭决策模型时显示一行警告：「自主模式下常驻记忆不会自动更新，仅 `memory_remember` 写入外部后端」。

## P5（已修复）常驻记忆的报错文案全错，用户会陷入死循环

超限、只读、revision 冲突在存储层都是异常，但 RPC 一律返回：

```
"Resident memory changed; reload and try again"
```

用户把 9000 字符粘进 8000 上限的框里 → 提示「被其他会话修改了，请重新加载」→ 重新加载 → 还是超长 → 永远保存不进去。

已按真实原因分流（新增回归测试覆盖 5 种 refusal）：

| 真实原因 | 修复前 | 修复后 |
|---|---|---|
| 内容超长 | 文档被他人修改，请重新加载 | 内容过长（上限 8000 字符），请先精简 |
| revision 冲突 | 同上 | 文档已在其他会话修改，请重新加载 |
| 只读 / 保留标记 | 同上 | 各自的准确说明 |

## P6（未修）`{project}` 展开会把不同仓库混成一个库

`projectId` 取自 `basename`，所以 `/a/foo` 和 `/b/foo` 都是 `foo`，展开后写进同一个 bank。
`projectKey` 有 16 位 hash 可以区分，但 bank 名没用它。

**建议**：bank 模板支持 `{projectKey}`，或默认在冲突时加短 hash。

---

## P7（未修）memos-bridge 子进程无回收

每个 runtime（按 identity 计）每个 memos-bridge backend 会常驻一个 `node dist/bridge.mjs` 子进程，`runtimes` 是无限增长的 Map，**没有 LRU、没有 idle 超时**。只有配置变化或插件卸载才 `killChild`。

当前机器上已有 2 个这样的常驻进程（一个来自 Hermes，一个来自本插件）。

**建议**：给 `runtimes` 加容量上限与 idle 回收（例如 10 分钟无请求就 dispose）。

---

## P8（未修）并行 `memory_remember` 必然丢一条

`retentionRouter` 用 `snapshot.writeRevisions` 做栅栏，成功后回写。**同一快照上的两次并发调用会读到同一 revision**，实测：

```
并行两条 remember -> ok error
```

模型一轮里并行发两个 `memory_remember`（DSH 默认 `maxParallelToolCalls: 10`）就会触发。

**建议**：在 `retentionRouter` 内部按 target 串行化，或冲突时自动重读 revision 重试一次。

---

## P9（未修）显式事实检索是朴素 bigram 重叠，几乎不筛

`explicitFactScore` 只做单字/双字交集计数，没有 IDF、没有归一化、没有阈值。实测「服务怎么启动」对着一条 DGX 端口事实得 1 分就算命中。

好在它只作为语义检索的附加层，且上限 3 条，危害有限。**建议**：加最低分阈值（≥2）与查询长度归一化。

---

## P10（未修）UI 层若干交互缺陷

| 位置 | 问题 |
|---|---|
| 使用范围 → 编辑 → 确定 | 只写 `scopeOverrides`，**无法新建绑定**（实测：只有 override 时生效 bindings 数 = 0）。用户以为配了，实际没生效 |
| 使用范围 → 删除 | 对「自动发现」的行删除无效果（没有对应 route 可删），但界面不提示 |
| 记忆系统弹窗 | `keyEnv`（环境变量名）被藏起来，只能填明文密钥；`apiKey` 与 `keyEnv` 语义差别用户不知道 |
| 系统标识 | 填了与已有系统同名的 id 会**静默覆盖**旧系统（registry 层面会拒绝重复，但 UI 先覆盖掉了） |
| 常驻记忆 tab | 文件超限时 `inspect` 整体抛错，**整个 tab 显示「读取失败」**，连其他正常文档也看不了 |

最后一条实测确认：

```
snapshot 抛错: Resident memory global-memory exceeds limit
inspect 抛错: Resident memory global-memory exceeds limit
```

**建议**：`inspect` 逐文件容错（超限的标红而不是整体失败）。
