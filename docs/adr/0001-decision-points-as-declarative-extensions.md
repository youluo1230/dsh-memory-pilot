# 0001 决策点作为可声明扩展单元

## 状态

已接受

## 背景

判断能力最初服务于记忆读写：要不要查、查哪个库、要不要记。当时「判断」和「记忆」在代码里是同一件事——问卷的字段名写死了 `recall_gate`、`scope_global`，记录结构里也带着这些词。

现在需要让它覆盖更多场景：浏览器操作前要不要执行、某条命令要不要确认、一次任务要不要拆解。这些判断与记忆无关，但用的是同一类模型：给定状态，在封闭选项里选一个，给出校准概率。

问题不在于能不能做，而在于**新增一个判断能力要付出什么代价**。如果每加一种判断都要改决策层的代码，那么这门能力就只属于插件作者，用户无法自行扩展。

## 决定

决策点（decision point）是扩展单元，并且可以是一份声明式配置：问卷、判据、触发点、落点动作四部分。用户能新增自己的决策点，不需要等插件发版。

落点动作是封闭集合（代码提供，如「跳过此操作」「询问用户」「注入上下文」），用户只能组合，不能凭空发明。

判据文本对用户可编辑，因为实测表明准确率主要取决于判据措辞而非模型本身：同一句 `rm -rf` 在一次测试里被判为 safe 74%，把判据写清楚后结果改变。

## 备选方案与未选原因

**只开放开关。** 最安全，但判据——影响准确率最大的部分——仍由作者垄断，用户遇到误判只能等发版。

**允许任意代码注册。** 最灵活，但用户要写 JS 才能加一个判断，门槛过高，且难以保证不阻塞主流程。

**连触发位置也开放配置。** 需要用户理解 hook 机制，前期不划算。触发位置先由插件内置并命名，用户只能选。

## 后果

用户新增决策点后，判据写错会导致判断静默失灵——没有报错，只是选择变差。这必须靠两件事兜住：

- 问卷提交前校验判据非空、选项至少两个、动作在封闭集合内
- 记录里保留问卷与答案，让用户能回看「它当时是怎么选的」

自动化等级由作者定默认值，用户只能收紧不能放宽。放宽意味着作者没设计过的误判会直接生效。
